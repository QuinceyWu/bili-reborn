# 防风控设计说明

目标不是「跑得最快」，而是**让请求序列在统计特征上接近人工操作**，并在被拦截时优雅降级。

## 1. 为什么会被风控

B站前端一次正常操作通常包含：打开页面 → 浏览 → 点击 → 一次写请求。而脚本化清理是**高频、等间隔、连续写请求**，特征非常明显：

| 特征 | 人工 | 朴素脚本 | 本项目的对抗方式 |
| --- | --- | --- | --- |
| 请求间隔 | 数秒到数分钟，方差大 | 恒定 0~200ms | 区间随机 + 抖动 |
| 连续写操作 | 很少超过 10 次 | 几百次不间断 | 每 15 次长休息 60~150s |
| 失败后的行为 | 停下来 | 立刻重试 | 指数退避 + 熔断冷却 |
| 单日总量 | 几十次 | 无上限 | 每日配额 |

## 2. 四层限流

### 第 1 层：请求级随机延迟

```js
// 均匀随机打底 + 三次均匀分布求和做类正态抖动
const base = randInt(cfg.delayMin, cfg.delayMax);                      // 1500 ~ 3500
const jitter = (Math.random() + Math.random() + Math.random() - 1.5) * 500; // -750 ~ +750
const wait = clamp(base + jitter, 500, 20000);
```

**为什么用三次均匀分布求和**：单个 `Math.random()` 是平坦分布，长时间采样后间隔会呈现明显均匀性；三个随机数相加近似正态，峰值集中在中间、尾部自然稀疏，更接近人的反应时间分布。

### 第 2 层：批次休息

计数器每累加 `batchSize`（默认 15）次，插入一次 60~150 秒的休息。

```js
if (count % cfg.batchSize === 0) {
  await sleepInterruptible(randInt(cfg.restMin, cfg.restMax));
}
```

这一层切断的是「连续请求数」这个特征，比单纯拉长间隔更有效。

### 第 3 层：指数退避

```text
wait(n) = min(8000 * 2^(n-1) + rand(0, 5000), 8min)

n=1 →  8s ~ 13s
n=2 → 16s ~ 21s
n=3 → 32s ~ 37s
n=4 → 64s ~ 69s   （默认 maxRetries=4，此后抛错终止）
```

退避期间的等待被切成 1 秒片，每秒检查任务状态，保证暂停/停止能及时生效。

### 第 4 层：熔断冷却

```text
        成功
  ┌──────────────┐
  ▼              │
 CLOSED ──风控×1──► CLOSED（计数=1）
   │
   ├──风控×2──► CLOSED（计数=2）
   │
   └──风控×3──► OPEN：冷却 15~30min ──► 计数清零 ──► CLOSED
```

熔断期间不发起任何请求，避免「越撞越死」——连续命中 412 后平台侧的限制窗口通常会长于单次退避。

## 3. 状态机

```text
idle ──start()──► running ──pause()──► paused ──resume()──► running
                     │                    │
                     └──── stop() ────────┴──► stopping ──► idle
```

实现要点：**协作式取消**。不使用 `AbortController` 强杀，而是在循环的两个安全点插入 `await Runner.gate()`：

- 请求发出前
- 单条记录处理前

`gate()` 在 `paused` 时挂起（轮询 400ms），在 `stopping` 时抛 `StopError`，冒泡到顶层被捕获，任务自然退出，不会留下半截请求。

长等待统一走 `sleepInterruptible(ms)`：

```js
function sleepInterruptible(ms) {
  let left = ms;
  async function step() {
    await Runner.gate();              // 暂停 / 停止检查点
    if (left <= 0) return;
    const s = Math.min(1000, left);
    left -= s;
    await sleep(s);
    await step();
  }
  return step();
}
```

## 4. 任务编排：先扫描，后执行

动态与关注都采用**两阶段**：

```text
阶段一（只读）：分页拉全量 → 得到稳定快照 → 过滤 → 输出待处理清单
阶段二（写）  ：按清单逐条执行，每条前过 gate + 限流 + 配额
```

好处：

1. **不会因为列表变化导致 offset 错位**（边删边翻页的经典坑）。
2. 开始删之前就能看到总数，演练模式下可先核对。
3. 中途停止后重跑，未处理的部分自然还在，幂等。

## 5. 每日配额

按自然日计数，键名 `baw:quota:YYYY-MM-DD`，超出 `dailyLimit` 后 `Quota.ensure()` 抛错终止任务。这是最后一道保险，防止挂机过夜把账号打穿。

## 6. 调参矩阵

| 场景 | delayMin/Max | batchSize | restMin/Max | dailyLimit |
| --- | --- | --- | --- | --- |
| 首次试水 | 3000 / 6000 | 10 | 120s / 300s | 200 |
| 稳健清理 | 1500 / 3500 | 15 | 60s / 150s | 600 |
| 小号快速 | 800 / 2000 | 30 | 30s / 75s | 1200 |

**已经吃过 412 的账号**：先用「首次试水」档跑一天，确认不再触发，再逐步收紧。

> 每日上限填 `-1` 表示不限量。不建议第一次就设 `-1`——配额是防「挂机过夜把账号打穿」的最后一道闸。

## 7. 不该做的事

- ❌ 并发请求（Promise.all 批量删）——这是最快触发风控的写法。
- ❌ 412 之后立刻无条件重试。
- ❌ 24 小时不间断挂机。
- ❌ 多账号共用同一浏览器会话轮换。
